# legal_department_management 19.0.7.0.0 — product and build specification

Status: **v1, written 2026-09-24** from the six research documents in
`docs/ldm/research/` (01 audit · 02 prototype · 03 departments · 04 offices ·
05 UX · 06 reuse). Where this document and a research document disagree, this
document wins; where this document and the live system disagree, the live system
wins and this document is corrected in writing.

---

## 0. What we are building, in one screen

One Odoo 19 Community module, **`legal_department_management`**, that runs the
whole working life of an **in-house legal department** (قسم الشؤون القانونية) and
of a **law office** (مكتب المحاماة), switched by one setting, built as an
**in-place upgrade** of SAG Group's production module 19.0.6.3.0.

The product is **matter-centric and template-driven**:

- Everything is a **matter** (`legal.task`, «ملف») with a **kind**: government
  transaction, lawsuit, execution, contract, opinion, corporate act,
  investigation, other. The kind decides which sections, tabs and clocks exist.
  That one decision removes most of the clutter.
- A **matter type** (`legal.task.template`) creates the work: steps with
  working-day offsets, required documents, the approval requirement, extra
  per-type fields (Odoo `properties`).
- The day starts on **مكتبي / My Day**, not on numbers: what is overdue, today,
  this week, with the reason and one action per row.
- Creating a matter is **one dialog with three to five answers**.
- The matter form is a **cockpit**: where it is, what is next, by when, who holds
  it, what it cost. It has one status axis and at most two visible header actions.
- **Iraqi clocks are data**: appeal, cassation, objection, execution and
  administrative periods, each with its legal basis and a verification flag,
  counted on a Sunday–Thursday calendar with holidays rolled forward (CCP Art. 25(2)).
- **Advanced is available and never in the way**: five disclosure layers
  (feature switch, role, mode, matter kind, and an in-form «المزيد» toggle).

## 1. Binding principles (every stream obeys these)

1. **Upgrade-safe.** Keep models `legal.task`, `legal.company`, `legal.ministry`,
   `legal.department`; their tables, stored columns, relation tables, selection
   **values**, and every xmlid listed in `research/01 §4.5`; the sequence code
   `legal.task`; the cron method `_cron_check_upcoming_sessions`; the client
   action tag `legal_dashboard_tag`; the three `report_name` strings. Changed
   meaning goes through `migrations/19.0.7.0.0/`. **No new required field on an
   existing record** (a required field gets a default or a migration fill).
2. **Self-contained.** No dependency on, import from, or xmlid reference to any
   other `legal_*` module. Porting code from them is allowed (same owner, LGPL-3).
   Manifest carries `'excludes': ['legal_core']`. Browser registry keys are
   prefixed `ldm_`, the CSS scope class is `o_ldm`.
3. **Production-safe.** Never write `res.company.currency_id`, never change a
   currency's rounding, never add users to groups, never create users with
   passwords, never ship reference data that can collide with SAG's
   unique-name constraints (bodies go through an opt-in merge import, §9.2).
   Demo data lives only under the manifest `demo` key.
4. **English source, complete Arabic.** Every string in Python, XML, JS and QWeb is
   English source with a complete `i18n/ar.po` (generated by `odoo-bin i18n
   export`, then filled). Zero untranslated entries; zero English on an `ar_001`
   screen; zero Arabic on an `en_US` screen except data. No emoji anywhere.
5. **Mode never gates data.** Modes and feature switches change vocabulary,
   menus, fields and defaults. Who can read or write what is decided only by
   groups, ACLs and record rules.
6. **Native first, OWL where it removes a step or a decision.** Lists, kanbans,
   calendars, pivots, graphs, settings and chatter stay native. OWL builds the
   home, quick-create helpers, cockpit widgets, dossier panel, palette provider,
   timer and other places where a native view needs extra steps.
   No React/Vue/jQuery, no core patches, and **no new runtime JS library**:
   Odoo 19 already ships everything needed (research/05 §7).
7. **Screen budgets** (checked by the harness): matter creation ≤ 5 inputs;
   form header ≤ 2 visible buttons plus one overflow menu; list ≤ 6 default
   columns; kanban card ≤ 4 lines; ≤ 7 top menu entries per non-manager role;
   the largest type on a screen is text, never a digit; every count opens the
   records it counted; empty states name the next action.
8. **RTL by logical CSS only** (`margin-inline-start`, `border-inline-start`);
   no inline `style=` in views; no `!important`; SCSS variables; dark-mode safe.
   `fa` icons carry `title` and `role="img"`.
9. **The auditor never gets a mutation affordance**: hidden in the UI and fenced
   by ACLs and rules.
10. **Server-enforced workflow.** State and approval transitions are enforced in
    Python (methods and `write`), never only by button visibility.
11. **Dates in the user's timezone** (`fields.Date.context_today`), Asia/Baghdad by
    default; money is `Monetary` with a `currency_id`.

## 2. Modes, presets and feature switches

### 2.1 Company settings

`res.company.ldm_mode` (selection, default `department` on a fresh install; the
upgrade migration sets `hybrid` for SAG because the data fits both):

| Value | Label (en / ar) | Vocabulary |
|---|---|---|
| `department` | In-house legal department / قسم قانوني | الشركات التابعة، المعاملات والقضايا |
| `office` | Law office / مكتب محاماة | الموكّلون، القضايا والملفات |
| `hybrid` | Both / كلاهما | الشركات والموكّلون (SAG's current label), neutral words |

Terminology is delivered by two technical groups implied from settings:
`group_ldm_terms_department` and `group_ldm_terms_office`. Base view labels are
the neutral set; per-mode inherited views restricted to those groups relabel a
small, fixed list of fields and actions (research/05 §9). Hybrid has neither
group, so it shows the neutral set.

### 2.2 Feature switches

Each switch is a `res.config.settings` boolean with `implied_group=` onto
`base.group_user` (the Odoo pattern), so a switch that is off leaves no menu,
field, column, button, tile or settings sub-section behind. Presets only set
switch values; they are not code paths.

| Group xmlid | Switch | Dept | Office | Hybrid | Solo lawyer |
|---|---|---|---|---|---|
| `group_ldm_government` | Government transactions (bodies, services, visits, required documents) | on | on | on | off |
| `group_ldm_litigation` | Lawsuits, hearings, judgments, appeal clocks | on | on | on | on |
| `group_ldm_approvals` | Approval before a matter proceeds | on | off | on | off |
| `group_ldm_poa` | Powers of attorney register | on | on | on | on |
| `group_ldm_correspondence` | Incoming/outgoing correspondence register (صادر/وارد) | on | off | on | off |
| `group_ldm_requests` | Requests from business units (every employee can submit) | on | off | off | off |
| `group_ldm_contracts` | Contract and opinion matters (kinds `contract`, `opinion`) | on | on | on | on |
| `group_ldm_corporate` | Company records: identifiers, document vault, recurring obligations | on | on | on | off |
| `group_ldm_billing` | Fees, fee agreements, invoicing, payments, client statements | off | on | on | on |
| `group_ldm_time` | Time tracking and the systray timer | off | off | off | off |
| `group_ldm_conflicts` | Conflict-of-interest check at intake | off | on | off | on |
| `group_ldm_hr_team` | Staff team from HR employees (`employee_ids`) | off | off | on | off |
| `group_ldm_accounting_links` | Post expenses to accounting (journal entry or payment) | off | off | off | off |

Other company settings (not groups): `ldm_calendar_id` (working calendar for
clocks, default the shipped Iraq Sun–Thu calendar), `ldm_visibility`
(`assigned` | `all`: whether lawyers see all matters; `all` implies
`group_ldm_see_all`), `ldm_approval_sod` (requester may not approve own matter,
default on), `ldm_conflict_policy` (`warn` | `block`), `ldm_fee_cap_check`
(Advocacy Law Art. 56, 20%), `ldm_reminder_days` (default 3), `ldm_poa_warning_days`
(default 30), `ldm_currency_ids` shown on settings (no write to company currency).

### 2.3 Presets

A one-question onboarding panel on the settings page ("What kind of organisation
is this?") and a selection `ldm_preset` on settings apply the column values above.
Changing one switch afterwards does not change the preset label.

**Guarantees, each with a test:** switching `department` → `office` adds no required
field to any existing record; a switch that is off leaves nothing visible; the mode
never changes a record rule.

explicit `(3, ref('group_legal_manager'))` on `base.group_system` plus migration
M11, which grants the manager role explicitly to every user who held it only
through `base.group_system` (so nobody loses access on upgrade day). The Settings
admin still sees the Legal settings section (settings are admin-only by Odoo).

### 3.2 Visibility (record rules; xmlids kept, domains rewritten)

- **Assigned** (clerk and lawyer; rules `legal_task_rule_lawyer` and a new clerk
  rule with the same domain): `lawyer_id = user` OR `user in lawyer_ids` OR
  `user in legal_company_id.lawyer_ids` OR `user in step_ids.user_id` (open steps)
  OR `user in hearing_ids.attending_user_id`. Confidential matters
  (`confidential = True`) drop the client-lawyer and step clauses.
- **All** (`legal_task_rule_manager`, `group_ldm_see_all`, auditor read, billing read).
- **Clients** (`legal_company_rule_lawyer`): responsible, lawyers, or has a visible matter.
- **Requests**: requester sees own; legal users see all requests.
- **Multi-company**: global rules `company_id in company_ids` on every model with
  `company_id`.
- Child records (hearings, steps, documents, expenses, deadlines, judgments,
  parties) follow the matter: rule `task_id` in the visible set, via
  `('task_id', 'any', [])`-style domains or `_check_company_auto` plus an ACL-matching rule.

### 3.4 Separation of duties and guarded fields

`models/ldm_engine.py` (port of `legal_core/models/legal_engine.py`, thread-local
marker, never a context key). Guarded fields: `approval_state`, `approver_id`,
`approval_date` on `legal.task`; `number` and `state` on a registered
correspondence; `state` of a POA after revocation. A write to a guarded field
outside `engine_guard()` raises `AccessError` for everyone except superuser
during migrations.

`legal.task.state` transitions are validated in `write()` (so a kanban drag or
an RPC write obeys the same table as the buttons):

| From → To | Allowed when |
|---|---|
| draft → in_progress | approvals off, or `approval_state = approved`, or the template does not require approval |
| in_progress ↔ pending_docs | always |
| in_progress / pending_docs → done | always (a closing dialog asks for the outcome, §5.8) |
| any open → cancelled | lawyer and above; reason required (dialog) |
| done / cancelled → in_progress (reopen) | manager only |
| any → draft | manager only, and only while `approval_state != approved` |

Approval: `action_request_approval` (responsible or manager), `action_approve` /
`action_reject` (approver group; with `ldm_approval_sod`, not the requester of the
approval), reject needs a reason; every decision logs to chatter with who/when/why.
Resubmission after rejection is allowed. After approval, `legal_company_id`,
`template_id` and `department_id` are locked (edit requires a manager reset).

## 8. Automation

- `_cron_check_upcoming_sessions` (kept entry point, daily): for each open item —
  hearings/visits within `ldm_reminder_days`, deadlines at T-3 and T-1 (working days),
  overdue targets, POA/document expiries within their warning windows — ensures **one**
  open activity per (record, user, reason), updating it instead of adding a new one;
  dates computed in the company timezone; unassigned items go to the matter's
  responsible, else to the legal managers, never to OdooBot. Idempotent (test: run twice,
  count unchanged). Escalation: a deadline at T-1 with no activity done notifies the
  managers.
- Obligations cron (daily): creates due matters from `legal.obligation`.
- Retainer cron (daily, billing): marks retainer schedule lines due and, with
  auto-draft on, prepares draft invoices.
- Deadlines: missed deadlines (past `date_deadline`, still open) become `missed` and
  notify the responsible and the managers.

## 14. Critique resolutions (binding; supersede the sections they name)

A four-lens critique (department manager, office partner, Odoo architect,
simplicity critic; 100 issues, full text in `docs/ldm/research/07-spec-critique.md`)
was run before the build. These decisions resolve it. Where §14 and an earlier
section disagree, §14 wins.

### 14.1 Clocks
- **Statutory periods are calendar days.** `last = event_date + N days` (or
  `relativedelta(months=N)`), counting from the day after the event (CCP Art. 25(1)).
  `date_safe = last`. `date_deadline` = the first working day on or after `last` on the
  effective calendar (court, then ministry, then company legal calendar) when
  `extends_on_holiday` (Art. 25(2)). `max_months` caps from the decision date.
  Working-day counting (`res.company.ldm_add_working_days`) is used **only** for
  template step offsets, `duration_days`, reply-due dates and reminder lead times.
  Required test: service Thu 2026-10-01 + 15 days: last day Fri 10-16, deadline Sun 10-18.
- Lists, My Day and the cockpit show **one "act by" date (`date_safe`)**; the legal
  last day appears on the deadline form, its tooltip and the judgment.
- Deadline state **`awaiting_service`** (no dates): created when a judgment is recorded
  without `notified_date`. Deadline generation is a method on `legal.judgment` called
  from `create`/`write` of `date`, `notified_date`, `pronounced_in_presence`, `law`,
  `court_degree`; idempotent per rule; recomputes open deadlines. My Day shows
  "awaiting notification" rows with an inline date; a palette command "Record notification".
- Rules gain `next_rule_id`, start events `previous_deadline_end` (silence counts as
  rejection) and `hearing_outcome`, and `trigger_outcome`. Hearing outcomes gain
  `left_for_review`, `suspended`, `stayed`, `interrupted`, `expert`, `witnesses`; the
  outcome dialog proposes CIV-9/10/11 from them; chains ADM-1 to ADM-2 to ADM-3/4 and
  EXE-1 to EXE-4 are tested.
- **`legal.holiday`** (manager-editable: name, date from/to, governorate, estimate flag)
  syncs into global leaves of the legal calendar with sudo, and on change recomputes
  open deadlines and open step dates in the range and notifies owners whose dates moved.
  2026 and 2027 shipped (Hijri dates marked estimates).
- `legal.deadline.escalated` so managers are notified once; escalation keys on the
  deadline's state, not on activities.

### 14.2 Security and visibility
- Child rules repeat the matter's assigned domain through `task_id.` paths (never
  `any`: rules are compiled as sudo). One generator script emits them.
- `group_ldm_see_all` rule = `['|', ('confidential','=',False), <assigned>]`; only
  manager and auditor read everything. Billing reads **non-confidential** matters only,
  and privileged text fields (`action_details`, `question`, `opinion_html`,
  `close_note`, hearing `outcome_note`) carry `groups` that exclude billing. v1 limit,
  documented: billing sees the chatter and files of non-confidential matters.
- Rules for correspondence (letters of confidential matters follow the matter), company
  documents (confidential: responsible and managers), POAs and obligations (all legal
  users; office-wide registers).
- Only the responsible and managers may change `lawyer_id`, `lawyer_ids`, `confidential`
  on a matter, and `lawyer_id`, `lawyer_ids` on a client (checked in `write`).
- `create()` never accepts a non-draft state or approval fields from a client; the
  state is applied after creation through the validated transition. `state`,
  `outcome`, `date_closed`, approval fields: `copy=False`.
- **Done and Cancelled only through their dialogs** (`engine_guard`); a bare write, a
  statusbar click or a kanban drop to them raises "Use Close matter / Cancel matter".
  The statusbar is not clickable. `close_note` carries the cancel reason.
- `create_from_template` always adds the creator to `lawyer_ids` (J1: a clerk who opens
  a matter for another lawyer's client can open it).
- Unlink of judgments, deadlines, hearings, expenses: managers only; others cancel.
  `mail.thread` and tracking on hearing, judgment, deadline, expense.
- Privileges: "Legal" = clerk < lawyer < approver < manager, and auditor (exclusive);
  "Legal billing" = billing. Feature, terms and see_all groups have no privilege.
- Account fields (`invoice_ids`, `invoice_line_id`, `move_id`, `payment_id`) carry
  `groups="account.group_account_invoice,account.group_account_readonly"`; billing
  states are computed with sudo.
- Clerk: R+C on `legal.conflict.check` (redacted hits), R on `legal.engagement`.
- Letter templates render from a flat dict of pre-computed escaped strings with a
  `string.Formatter` that rejects `.` and `[` in field names.
- `group_legal_user` keeps implying `base.group_partner_manager` (lawyers must create
  parties and counterparties); stated in the upgrade notes as the one rights change.

### 14.3 Settings, modes, terminology
- **Mode, preset, switches and visibility are database-wide** (they are groups):
  `ldm_mode`, `ldm_preset`, `ldm_visibility` are `ir.config_parameter`s behind the
  settings. Per company: calendar, reminder days, POA warning days, SoD, conflict policy,
  fee cap, engagement-required. Settings are admin-only (Odoo's rule); managers edit
  holidays, matter types, bodies and templates from Configuration.
- **One question**: "Kind of organisation" = `department`, `public` (public-sector legal
  department), `office`, `solo`, `hybrid`. It sets the mode and the switches; switches
  stay editable under "Customise".
- **Always on (no switch):** litigation, POAs, contracts, opinions, bodies and courts,
  the documents checklist. **Switches:** government transactions, approvals,
  correspondence register, requests, company records (vault, obligations, guarantees,
  coverage), investigations (public sector), fees and billing (sub-options: time,
  conflict check, client messages), and under "Advanced": HR staff team, accounting
  links. `group_ldm_litigation`, `group_ldm_poa`, `group_ldm_contracts` are removed.
- The government switch hides only the government kind and its types, visit steps,
  services on bodies, obligations and the reference import. Bodies and courts,
  `department_id` and the documents checklist are core (Solo can record a hearing).
- Fresh install: a `post_init_hook` applies the `department` preset. Upgrade: M14
  applies `hybrid` unconditionally.
- **Terminology:** menus, actions and reports use one neutral vocabulary. The mode
  relabels only the client label on the matter form, the client form title and My Day,
  through duplicated label nodes with positive/negative `groups` in the primary arch
  (inherited views cannot carry groups in Odoo 19). OWL reads `user.hasGroup`.
- IQD: module views, OWL and reports display IQD with 0 decimals through a shared
  helper; an admin-only Settings action "Show IQD in whole dinars" (sets rounding to 1)
  is offered only when no posted accounting entry uses IQD.

### 14.4 Matter model and screens
- `next_date` is **stored** (earliest open hearing, open visit step, open deadline
  `date_safe`, open step, target date) and indexed; `next_action` stays non-stored.
- `date_state_changed` (stored) replaces `statusbar_duration` (Selection is not
  supported) and shows as a vital ("in this stage for 6 days").
- Government: `waiting_on` (us, body, client, verification), `date_submitted`,
  `days_at_body` (working days, body calendar), `target_days` on template (fallback
  body); manager band and filter "At the body past target".
- **A visit is a step** (`is_visit`), never a hearing. The visit dialog updates the step,
  stores receipt number, fee and photo, and creates exactly one expense line.
  `legal.hearing` = court sessions and meetings only (no visit kind, no visit outcomes,
  no `postponed` state, no receipt or fee). M5 migrates non-court `session_date` values
  into visit steps. `session_date` = earliest planned hearing or open visit step.
- **Court stages:** `legal.court.stage` lines (stage, court, case number, year, date
  filed, judgment, execution file number and notification date). `court_case_number`
  and `court_stage` on the matter mirror the latest line. Judgments gain `final_date`
  and `amount_awarded`.
- Post-approval lock covers `legal_company_id`, `template_id`, and `department_id` only
  for kind government.
- Investigation kind (public mode): order number and date, issuing authority, committee
  members, employees concerned, recommendation, decision number and date, compensation
  (تضمين) amount; `confidential_default` on templates (true for investigations).
- Opinions: `action_issue_opinion` (yearly number, frozen by `engine_guard`, memo PDF
  attached), `supersedes_id` / `superseded_by_id`, `requesting_unit`, register filter
  with full-text search.
- Single opponent source: S2's opponent input creates a party line (existing partner
  first); `opponent_name` becomes a stored compute from the parties.
- Client phone and email become related to the partner (readonly=False), created and
  synced in `create`/`write`; `company_type` loses `individual` (that is `client_kind`).
- Ship a generic "Government transaction" type (no default body) in module data; the
  migration ensures it exists. S2 shows the body as a visible input when the type has
  no default body and the kind is government or litigation; the body picker searches
  ministry names too.
- Menus: no top-level "New matter" (xmlid kept, hidden); Approvals is a top-level leaf
  (folder xmlid kept, archived); requesters get their own root app; Registers carries a
  read-only "Bodies and courts" directory; My Day for clerk and above only (auditor and
  billing land on Matters). The Matters action drops the calendar view.
- Cockpit: statusbar read-only; one overflow dropdown drawn by the `ldm_matter_form`
  js_class for buttons with class `o_ldm_more`; the contextual action lives on the
  next-step card; the approval banner replaces the card while pending; litigation shows
  the phase rail and no progress %. No "Details" tab: one collapsible "More" group at
  the bottom; properties render inline on the main page; `court_case_number`
  (litigation) and `reference` (government) in the title line. `res.users.settings`
  gains `ldm_show_advanced` and `ldm_recent_template_ids`.
- Widgets (W): `ldm_step_checklist` (one-click tick with Undo), `ldm_document_checklist`
  (per-row drop and camera, state chips), an approvals list js_class with a read-only
  preview pane, and the Agenda as an OWL client action (hearings, visit steps and
  deadlines by day; Month opens the native hearing calendar; Print roll).
- My Day: includes the user's open activities on legal records; completing a source
  record closes its reminder activity; clerk "by body" grouping of today's visit steps
  with the documents to carry; manager bands "tomorrow's sessions without a lawyer",
  "conflicts awaiting your decision", "at the body past target"; Undo only for step
  completion.
- Hand-over wizard (W): from-user, to-user, optional end date, scope checkboxes
  (responsible/team, open steps, planned hearings, open deadlines, activities,
  requests); POAs where the leaver is an agent are listed as "new POA needed".
- Reminders use one `mail.activity.type` per reason and match on
  (res_model, res_id, user, type, summary); timezone from the legal calendar.

### 14.5 Money
- **Client funds in v1** as an operational ledger `legal.client.fund.line` (client,
  matter, date, type deposit/disbursement/execution_collection/transfer_to_fees/refund,
  amount, currency, receipt, attachment); balance per client and currency never
  negative (manager override with a reason). An expense with `paid_by=client_funds`
  writes the disbursement. GL posting stays v1.1.
- **Runner advances** `legal.advance` (employee, amount, currency, date, purpose,
  matter, state draft/paid/settled); settlement links employee-paid expenses; the
  balance shows on the clerk's My Day.
- Fee cap: fixed + success% × value ≤ 20% × Σ value of the linked non-criminal matters,
  converted to the engagement currency; `success_percent` allowed with any fee type;
  activation over the cap needs a manager and `cap_override_reason`. `law_branch` on
  matter and template (civil, commercial, personal_status, labour, criminal,
  administrative, other) drives the exemption, the rule choice and the licence check.
- Schedule lines use `trigger_event` (signing, filing, judgment_first_instance,
  judgment_final, execution_opened, collection, closing, date, manual) fired by the
  workflow; settle/withdraw/revocation proposes the remaining lines (Art. 58).
  `per_transaction` / `per_hearing` create due lines on matter done / hearing held;
  retainer lines are generated on activation; Bar minimum warning (300k/600k IQD,
  settings flagged "verify").
- S2 (office, billing on): optional fee-agreement input (existing engagement or a new
  draft); cockpit chip "no signed fee agreement"; setting `ldm_engagement_required` (warn).
- Conflict check: decision `pending` plus "send to the partner"; the matter stays draft
  until decided; re-run on parties, opponent, counterparty or client change; sources:
  clients including archived, parties and opponents on all matters including closed,
  counterparties, `commercial_partner_id` expansion, active retainer clients;
  immutable once decided.
- Client messages (switch `group_ldm_client_messages`): an `ldm_whatsapp` helper with
  Iraqi phone normalisation (07…, +964, 00964 to 964…), templates (hearing result,
  hearing reminder, missing documents, instalment due, statement ready) in the partner's
  language; each use posts a chatter note.
- Close dialog (billing mode): unbilled expenses, remaining schedule, balance due, funds
  balance, originals held (`original_held` on documents), linked POA. Outcomes gain
  `client_revoked` and `lawyer_withdrew`.
- Statement per currency from `amount_currency`, with unbilled expenses and the future
  schedule; one invoice per currency.
- Expense approval threshold: **removed from v1**.

### 14.6 Registers
- Requests: the requester writes only name, description, needed_by and attachments,
  and only while new or returned; "Resubmit"; `request_type` maps to a default template;
  `legal_company_id` is set by legal staff at triage (hidden from requesters); "Send
  result to requester". State, task, assignee and return reason are guarded.
- Correspondence: `sender_ref`, `sender_date`, `received_date`, `referred_by`,
  `referral_note`, `instruction_due` (a deadline), "Open matter from this letter",
  `signatory_id`, `signatory_title`, cc lines, `addressee_title` on bodies, a register
  book report, letter `lang` (default ar_001).
- "New document from template" on the matter in every mode (renders to editable HTML
  and a PDF attached to the matter); the correspondence switch controls numbering only.
- Guarantees `legal.guarantee` (bid, performance, advance payment; bank, amount, expiry,
  state, extension and release) behind the company-records switch.
- Substitution: `substitute_partner_id` on hearings, a `needs_substitution_letter`
  compute, and a substitution-letter report independent of correspondence.
- Monthly status report with a date range; exposure pivot by `our_role`. The auditor
  role is renamed "Auditor / executive (read only)".
- Licence classes ordered trainee, A, B, C, unrestricted; warning when a trainee
  attends an appeal, cassation or felony court.
- Coverage: SQL view `legal.company.coverage` (company × templates with
  `track_coverage`), a dossier tab and a grouped list with "Start"; a "Readiness at
  date" dialog for tender packs; S2 may create one matter per selected client.
